Frontend vocabulary · Reference

Frontend terminology,
plain English

Libraries, frameworks, meta-frameworks, build tools, rendering strategies — here's what they actually mean and how they relate to each other.

UI libraries & frameworks
what you build components with
UI library
aka "frontend library"
A collection of tools for building user interfaces. Handles how components render, update, and react to data changes. Does not decide routing, data fetching, or project structure — you wire those up yourself.
React Solid Preact
UI framework
aka "frontend framework"
Like a library but more opinionated. Comes with built-in conventions for routing, state management, and project structure. More decisions made for you — less flexibility, faster initial setup.
Vue Angular Svelte
you use this
React
library, not a framework — despite the name
React only handles the UI layer. You choose your own router, data fetching strategy, state management, etc. This is why meta-frameworks exist on top of it. Most widely used — ~40% of developers.
most widely used library only
Meta-frameworks & build tools
what you use to structure a full app
Meta-framework
aka "app framework" or "full-stack framework"
Sits on top of a UI library and adds everything it's missing: file-based routing, server-side rendering, API routes, build optimization, and deployment config. Turns a library into a complete application structure.
Next.js Remix Nuxt SvelteKit
you've used this
Next.js
React meta-framework — built by Vercel
The most popular meta-framework for React. Adds file-based routing, server-side rendering, image optimization, and API routes. With Next.js you can write both your frontend and a lightweight backend in one project.
React + routing + SSR API routes built in
you've used this
Vite
build tool — not a framework
A fast build tool and local dev server. It compiles, bundles, and hot-reloads your code. It is not a meta-framework — no opinions about routing or rendering. Think of it as the engine room powering the project, not the project itself.
build tool only replaces webpack
Rendering strategies
how & where your HTML gets generated
CSR
Client-side rendering
The server sends a nearly empty HTML shell. The browser downloads your JS bundle, runs it, and builds the entire UI in the browser. Fast after initial load, slower first paint. What plain React + Vite does by default.
Vite + React Create React App
SSR
Server-side rendering
The server generates full HTML on each request and sends it to the browser. Faster first paint, better SEO. The browser then "hydrates" the static HTML with React so it becomes interactive. Good for dynamic, user-specific pages.
Next.js Remix
SSG
Static site generation
HTML is generated once at build time, not per request. Blazing fast, great for content that doesn't change often like blog posts or docs. Not suitable for dynamic, user-specific data like saved trips or auth.
Astro Gatsby Next.js (static mode)

What this means for the parks app
The decision

Which setup makes sense here?

The parks app is dynamic and user-specific — saved trips, auth, real-time search. SSG is out. The real choice is how much structure you want up front and how much you want to learn by wiring things yourself.

React + Vite + Express
Two separate projects. You wire up every layer yourself — routing, API calls, proxy. More to configure, but you understand every seam. Best for interview prep.
Next.js ★
One project. File-based routing, API routes built in, SSR out of the box. Faster to ship, closer to real-world usage. The proxy can live as a Next.js API route.
React + separate Express
React frontend, Express backend, clearly separated. Good middle ground — you learn the layers but don't have to set up a full build pipeline yourself.
