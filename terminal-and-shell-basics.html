Terminal, shell
& CLI basics

What the terminal actually is, how the shell works, what PATH means, and the commands you'll use every day as a backend developer.

Terminal vs shell — not the same thing
The window

Terminal

An application on your Mac that gives you a text-based interface to your computer. Instead of clicking icons, you type commands and see text output. On macOS it's called Terminal — you might also use iTerm2.

The terminal is just the display layer. It shows you what's happening but doesn't do the thinking itself.

The interpreter

Shell

The program running inside your terminal. It reads what you type, figures out what to do with it, runs programs, and shows you the output. Your Mac uses zsh by default.

You might also hear about bash — an older shell, still common on Linux servers. The commands are mostly identical.

The analogy

The terminal is a TV set. The shell is the channel playing on it. The TV just displays things — the channel decides what you're watching. You could swap the channel (run a different shell) in the same terminal window.

CLI — Command Line Interface

You'll also hear the term CLI — it just means any tool you interact with by typing commands instead of clicking a GUI. The terminal is a CLI. psql is a CLI. npm is a CLI. When someone says "run this in the CLI" they mean "type this in your terminal."

What PATH is and why it matters

When you type a command like psql or node, the shell doesn't magically know where that program lives on your computer. It searches through a list of directories called the PATH — in order — until it finds a match. If it finds it, it runs it. If not, you get "command not found."

This is why we added PostgreSQL to your PATH earlier. Without that line in ~/.zprofile, typing psql would fail even though PostgreSQL was installed.

1
You type a command
$ psql --version
2
Shell searches your PATH directories in order
/opt/homebrew/opt/postgresql@16/bin → found psql here ✓
If not found, it keeps searching. If not found anywhere → "command not found"
3
Shell runs the program with your arguments
psql (PostgreSQL) 16.13
The analogy

PATH is like a list of drawers the shell checks in order. You say "find me a pen." It opens drawer 1 — no pen. Drawer 2 — found one. It stops searching and hands it to you. If no drawer has a pen: "command not found."

~/.zprofile — your shell's config file

The file ~/.zprofile runs every time you open a new terminal window. It's where you put things you always want set up — like PATH additions. The ~ is shorthand for your home directory (/Users/christysheppard). The dot prefix means it's a hidden file — Finder won't show it by default but the terminal can see it.

psql meta-commands — the backslash commands
Why the backslash? Inside the psql shell, regular text gets sent to PostgreSQL as SQL. Backslash commands are handled by the shell itself before anything goes to the database — they're instructions to psql, not to PostgreSQL. SQL needs a semicolon to terminate. Backslash commands don't.
CommandWhat it doesNotes

\c dbname Connect to a different database \c parks_dev
\dt List all tables in the current database Use after \c to a database first
\d tablename Describe a table — shows columns, types, constraints \d users
\di List all indexes Useful for performance debugging
\dn List schemas Usually just "public" for simple apps
\timing Toggle query execution time display Handy for performance checks
\q Quit psql and return to shell Or Ctrl + D
npm — Node Package Manager

npm ships with Node.js and does two related things: it manages the packages (libraries) your project depends on, and it lets you run scripts defined in your package.json. When you install a package, npm downloads it into a node_modules folder and records it as a dependency in package.json.

npm init -y
Initialize a new Node.js project in the current folder. Creates package.json with defaults. The -y skips interactive questions.
npm install package
Install a package and add it to dependencies in package.json. Short form: npm i package.
npm install -D package
Install as a dev dependency — only needed during development, not in production. Example: testing libraries.
npm install
Install all dependencies listed in package.json. Run this after cloning a repo — node_modules is never committed to git.
npm run scriptname
Run a script defined in the "scripts" section of package.json. Example: npm run dev, npm run build.
npm uninstall package
Remove a package and update package.json. Also removes it from node_modules.
What package.json actually contains
package.json — your project's ID card
"name"
The project name. Used if you ever publish to npm, otherwise just for identification.
"version"
Semantic version number. Format is major.minor.patch — e.g. 1.0.0. Matters more for published packages.
"main"
The entry point file — what runs when someone imports your package. For the parks API this will point to your Express server file.
"scripts"
Shortcuts you define and run with npm run. You'll add "dev" to start your server and "start" for production.
"dependencies"
Packages your app needs to run in production. Added automatically when you npm install a package.
"devDependencies"
Packages only needed during development — testing tools, linters, type checkers. Added with npm install -D.
"type"
Set to "module" for ES modules (import/export syntax) or "commonjs" for require() syntax. We'll use "module" for the parks API.
