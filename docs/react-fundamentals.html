React · Interview essentials

React fundamentals

Hooks mechanics that go deeper than "here's how you use useState" — the functional updater form, what mount/render/unmount actually mean, why cleanup fires on more than just unmount, the Rules of Hooks, when memoization actually helps, and controlled vs. uncontrolled components.

The functional setState updater form
// Broken — only ends up +1, not +2 function handleClick() { setCount(count + 1); setCount(count + 1); }
// Fixed — correctly +2 function handleClick() { setCount((prev) => prev + 1); setCount((prev) => prev + 1); }

prev isn't special to React — it's just a parameter name you chose, the same as any function parameter. setCount accepts either a plain value or a function. Pass a value, and React just uses it directly. Pass a function, and React calls it with whatever's currently queued as the pending state, using that result as the new value — which means a second queued function-update in the same handler gets fed the output of the first one, not a stale snapshot.

Contrast that with setCount(count + 1): count there is a plain variable captured from this render's closure — a frozen snapshot of what count was when this render happened. Calling it twice in the same handler reads that identical frozen value both times, so both calls compute the exact same result. It's not that the first update "got lost" — neither call updates anything immediately; both were queued using identical input before either was ever applied, and React processes the queue down to one net change.

Render vs. mount vs. unmount
The analogy

A render is the curtain going up — could be the premiere, could be the 50th performance. Mount is specifically the premiere: the one-time event where the component didn't exist yet and now it does. Every mount is a render, but only the very first render of a component's lifetime counts as its mount.

The dependency array isn't really "runs after mount, and separately again when deps change" — that's two mechanisms where there's actually only one: React re-runs an effect after any render where a listed dependency's value differs from what it was on the previous render. Mount always qualifies, for a simple reason — there is no previous render to compare against yet, so React treats that as "everything changed" by default.

Unmount is the component being removed from the DOM entirely — conditionally rendered away ({isVisible && <Counter />}), navigated off, or its key changed. If that same component comes back later, that's a brand-new mount, not a resumed one — fresh state, fresh effects, no memory of before. Concretely: unhiding a conditionally-rendered <Counter /> resets its count back to 0, every time, because it's a different component instance than the one that existed before it was hidden.

Cleanup fires on a re-run AND on a true unmount — same function, two triggers
useEffect(() => { console.log('Effect running for count:', count); return () => { console.log('Cleanup — count was:', count); }; }, [count]);

Clicking a button that changes count logs "Cleanup" on every single click — and that's correct, not a bug. When a dependency changes, React calls the previous run's cleanup right before the effect re-runs, then runs it again with the new value. The component is still fully alive through this — nothing was unmounted. Cleanup's job is to undo whatever the previous run set up, before the next run starts, regardless of whether "next" means "a fresh render with new deps" or "gone forever."

You'd only see the true unmount trigger by actually removing the component from the tree (toggling {isVisible && <Counter />} off) — that fires cleanup exactly once, with nothing following it. This is exactly why an AbortController cleanup in a data-fetching effect matters: if a dependency like url changes mid-fetch, cleanup aborts the stale in-flight request before the effect re-runs and kicks off a new one for the new value — same mechanism as the console.log example, just with a network call instead of a log line.

React 18 Strict Mode's double-invoke (dev only)

Vite's react-ts template wraps your app in <React.StrictMode> by default. In development only, Strict Mode intentionally mounts a component, immediately runs its cleanup, then mounts it again — specifically to help surface effects with missing or broken cleanup, by making the mount/unmount/remount cycle happen on purpose rather than waiting for you to stumble into it.

So a logging effect on mount often shows a rapid "mounted" / "cleaning up" / "mounted" pattern the very first time a component appears — that's Strict Mode doing its job, not a bug in your code. It only happens in development; production builds mount once, exactly as you'd expect. If your cleanup function is missing or incomplete, this double-invoke is what makes that obvious early, in dev, instead of silently leaking in production.

Why the useEffect callback itself can never be async
// Wrong — implicitly returns a Promise useEffect(async () => { const res = await fetch(url); // ... }, [url]);
// Right — inner async function, called immediately useEffect(() => { async function load() { const res = await fetch(url); } load(); }, [url]);

The function passed directly to useEffect is only allowed to return either nothing, or a cleanup function. Marking that outer function async makes it implicitly return a Promise instead — that's just how async functions work in JS — and React would then try to treat that Promise as the cleanup function, which breaks things silently. The fix is always the same shape: define a separate inner async function and call it, rather than making the effect callback itself async. A plain synchronous effect (a console.log with no await anywhere) never runs into this at all — the rule only bites once real async work is involved.

Rules of Hooks: condition the value, never the call
function Fixed({ showExtra }) { const [name, setName] = useState('Alice'); const [age, setAge] = useState(30); // always called → always same slot → always correct const [email, setEmail] = useState('a@example.com'); return <div>{name} / {showExtra ? age : null} / {email}</div>; }

That's the entire fix for a conditional-hooks bug — full stop, no useEffect required. showExtra ? age : null is completely fine: conditioning what you do with a hook's returned value is normal, ordinary React. What's never allowed is conditioning whether the hook gets called at all. React tracks hook state by the order hooks are called in, not by name — so wrapping a hook call itself in an if shifts every hook after it into the wrong slot the moment that condition changes between renders.

This applies identically to every hook, not just useState — wrapping useEffect itself in if (showExtra) { useEffect(...) } is just as broken, same slot-shifting disease, different hook. The fix is always the same shape: call the hook unconditionally, and move the if check inside its body/callback instead — e.g. useEffect(() => { if (!showExtra) return; ... }, [showExtra]).

useMemo vs. useEffect for a derived value
// useEffect version — costs a stale flash + extra render const [stats, setStats] = useState({ total: 0 }); useEffect(() => { const total = filtered.reduce(...); setStats({ total }); }, [filtered]);
// useMemo version — no flash, no extra render const stats = useMemo(() => { const total = filtered.reduce(...); return { total }; }, [filtered]);

Walking the useEffect version step by step: filtered changes → component re-renders, but stats is still whatever it was before (effects run after a render commits to the screen, not during it) → the user visibly sees stale numbers painted → the effect then runs, computes the real values, and calls setStats(...) → that state update triggers a second re-render, only now showing the correct numbers. Two full render cycles, plus a piece of state that exists only to hold something 100% derivable from filtered.

useMemo instead runs synchronously during the render itself — by the time this component's JSX is returned, stats already reflects the current filtered. No catch-up step, no flash, no extra state. The generalizable principle: useEffect exists to synchronize with something outside React (subscriptions, fetches, DOM APIs). Deriving one in-hand value from another isn't synchronizing with anything external — it's just a calculation, and calculations belong directly in the render body, with useMemo layered on only once that calculation is expensive enough to be worth caching. (You could skip useMemo entirely too — plain inline calculation, no hook at all — and still avoid the flash; the hook only earns its keep past a real cost.)

useMemo, useCallback, React.memo — what actually connects them
The foundational thing to understand first

Every time a component re-renders, any function or object created inside that render is a brand-new value in memory, even if it does exactly the same thing as last time: const fn1 = outer(); const fn2 = outer(); fn1 === fn2 is false. Normally this is completely harmless — React just calls whatever function is there, and never checks whether it's "the same one as before." It only becomes a problem the moment something else starts comparing that value's identity between renders — which is exactly what React.memo and dependency arrays do.

// useMemo — caches a computed VALUE const stats = useMemo(() => expensiveCalc(filtered), [filtered]); // useCallback — caches a FUNCTION REFERENCE const handleFilterChange = useCallback((key, value) => { setFilter(key, value); }, [setFilter]); // React.memo — skips a re-render when props are shallowly unchanged export const DataTable = React.memo(function DataTable() { /* ... */ });

useCallback only matters when something is actually comparing that function's identity between renders. There are exactly two real cases: the function is passed as a prop to a React.memo-wrapped child (memo's whole job is comparing new props to old, and an unstable function reference always looks "changed" even when the logic is identical, defeating the memoization) — or the function is used inside another hook's dependency array elsewhere, same problem, different consumer of the comparison. If neither applies, a fresh function every render is free, and useCallback is pure overhead.

That's also the catch tying React.memo back to useCallback: memo only helps if the props it's comparing are actually stable. A parent passing a freshly-created callback every render defeats a memoized child's whole purpose — the prop check reports "changed" regardless. memo does the comparing; useCallback is what makes that comparison actually succeed. Honest caveat for all three: they exist to fix a measured re-render problem, not something to reach for by default — using them without a real performance issue just adds complexity for no benefit. And specifically for useMemo: it's officially a performance hint, not a guarantee — React is technically permitted to discard a memoized value and recompute it in rare cases (e.g. memory pressure), so never rely on it for correctness (like preserving object identity for a === check), only for performance.

Controlled vs. uncontrolled components
// Controlled — value comes from state, every change routes back into it const { filters, setFilter } = useDataStore(); // filters starts as {} <select value={filters.category || ''} onChange={(e) => setFilter('category', e.target.value)} > <option value="">All Categories</option> <option value="marketing">Marketing</option> </select>

Tracing the chain: filters starts as {}, so filters.category is undefined → undefined || '' evaluates to '' → the select's value is '', matching "All Categories," which is why that one shows selected initially. Pick "Marketing": onChange fires → setFilter('category', 'marketing') → the store updates to { category: 'marketing' } → the component re-renders → filters.category || '' now evaluates to 'marketing' → the select updates to show it. The DOM never "owns" the value at any point in that chain — every change flows user action → onChange → state update → re-render → JSX reflects the new state. That round trip, not just "value comes from a variable," is what "controlled" means in practice.

An uncontrolled component instead lets the DOM hold the current value; React doesn't track it on every keystroke. You read it only when needed — typically via a ref (inputRef.current.value) — and set an initial value with defaultValue rather than value. Controlled gives you live validation, easy programmatic resets, and one source of truth across related inputs, at the cost of a re-render per keystroke (rarely an actual problem). Uncontrolled is simpler for "just grab the value at submit time" and skips that per-keystroke render, but makes live validation or an external reset harder, since the value isn't known until you go look at the DOM for it.

Two things worth having cold: <input type="file"> cannot be controlled — browsers disallow programmatically setting a file input's value for security reasons (a page shouldn't be able to fake a file selection), so it's always uncontrolled, read via a ref. And the classic warning, "A component is changing an uncontrolled input to be controlled", happens when state starts as undefined (React treats the input as uncontrolled on the first render) and later gets a real value, flipping it to controlled mid-life — React doesn't allow switching modes. The fix: always initialize state to a defined value ('', not undefined), so the input is controlled from the very first render onward.

Interview-ready reasoning
What to say when this comes up

Naming these concepts under pressure

  • Functional updater: "the plain-value form reads a frozen closure snapshot; the function form gets fed whatever's actually pending" — that's why two `setCount(prev => prev + 1)` calls stack and two `setCount(count + 1)` calls don't.
  • Mount vs. render: "mount is just the name for a component's first render" — the dependency array is one rule (rerun when a dep differs from last render), not two separate mechanisms.
  • Cleanup: "the same cleanup function fires before a re-run AND on a true unmount" — know the difference by whether the component is still alive afterward.
  • Rules of Hooks: "condition the value, never the call" — hooks track state by call order, not by name.
  • useMemo vs. useEffect: "useEffect synchronizes with something outside React; deriving a value from data you already have is just a calculation" — and know it's a performance hint, not a correctness guarantee.
  • useCallback: "only matters when something compares function identity between renders" — `React.memo`'s prop check or a dependency array, nothing else.
  • Controlled vs. uncontrolled: "does the DOM own the value, or does state?" — and know file inputs are always forced uncontrolled.
