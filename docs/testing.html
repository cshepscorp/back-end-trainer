Testing backend code

Unit vs. integration vs. end-to-end, what mocking actually buys you, and how to answer "how would you test this?" in an interview.

The testing pyramid
Unit tests — most of them

Test one function or module in isolation. Fast, cheap, run in milliseconds. Mock anything external (the database, a third-party API).

Integration tests — some of them

Test how pieces work together — an Express route hitting a real (test) database. Slower than unit tests, but catch bugs at the seams.

End-to-end tests — the fewest

Drive the whole app like a real user would, browser included. Slowest and most brittle, but validate the entire flow actually works.

The analogy

Unit tests taste one ingredient. Integration tests taste the dish coming together. End-to-end tests taste the final plate as a customer would. You want a lot of the cheap, fast ingredient checks, and only a few full-meal tastings — not the other way around.

Mocking — isolating the thing you're actually testing

A mock is a fake stand-in for something your code depends on — a database call, a third-party API, the current time. You replace the real thing with a controllable fake so your test is fast, deterministic, and actually testing your logic, not whether the network is having a good day.

// Without mocking — slow, flaky, hits a real DB test('creates a user', async () => { const user = await createUser( db, 'a@b.com' ); expect(user.email).toBe('a@b.com'); }); // depends on a real, running database
Fragile — needs real infrastructure to run
// With mocking — fast, isolated, deterministic const mockDb = { insert: jest.fn().mockResolvedValue( { email: 'a@b.com' } ) }; test('creates a user', async () => { const user = await createUser( mockDb, 'a@b.com' ); expect(user.email).toBe('a@b.com'); });
Runs anywhere, in milliseconds, every time
What to actually test, when asked live

Given a function in an interview, don't just test the happy path. Interviewers are listening for: the normal case (valid input, expected output), edge cases (empty array, zero, null, the boundary of a range), and error paths (what happens when a dependency throws, or input is malformed). Naming all three categories out loud, even briefly, signals real testing instinct.

TDD — red, green, refactor
The cycle

Red: write a failing test for behavior that doesn't exist yet. Green: write the minimum code to make it pass. Refactor: clean up the code with the safety net of a passing test behind you. You don't have to practice strict TDD to know the cycle — interviewers mostly want to hear that you write tests before you're confident the code already works, not only after something breaks in production.

Interview-ready reasoning
What to say when this comes up

"How would you test this endpoint?"

  • Unit test the logic — pure functions, validation, business rules — with dependencies mocked out.
  • Integration test the route — use something like supertest to hit the real Express app against a test database, confirming the whole path works together.
  • Cover the edge and error cases explicitly — not just "it works," but "it fails correctly" too.
  • Keep the pyramid shape — lots of fast unit tests, fewer integration tests, a handful of true end-to-end tests for critical flows only.
