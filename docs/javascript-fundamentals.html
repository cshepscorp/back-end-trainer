JavaScript fundamentals

The language-level questions that show up regardless of framework — closures, this, the event loop's microtask/macrotask split, prototypes, and the array/object methods that come up constantly in whiteboard exercises.

Closures
The analogy

A closure is a backpack of variables a function carries with it wherever it goes. When a function is defined inside another function, it keeps a reference to the variables from that outer scope — even after the outer function has already finished running and would otherwise have its variables cleaned up. The inner function packed them in its backpack on the way out.

function makeCounter() { let count = 0; // this returned function "closes over" count return function() { count++; return count; }; } const counter = makeCounter(); counter(); // 1 counter(); // 2 — count persisted between calls

This is exactly how the module pattern and private state in JavaScript work before classes had private fields — count is only reachable through the returned function, not from outside makeCounter at all. It's also the source of the classic loop bug: a var inside a for loop is shared across every iteration's callback (one shared backpack), while let creates a fresh binding per iteration (a new backpack each time) — which is why let fixed a whole category of "why did every callback log the same last value" bugs.

"this" — determined by how a function is called, not where it's defined

Unlike most variables, this isn't fixed by where a function is written — it's set fresh depending on how the function is called. Call it as obj.method() and this is obj. Call that same function detached, as a bare reference, and this is undefined (in strict mode/modules) or the global object. This is why passing obj.method directly as a callback — to setTimeout, an event listener, an array method — silently loses its this binding.

// breaks — this is lost class Timer { constructor() { this.count = 0; } tick() { this.count++; } } const t = new Timer(); setTimeout(t.tick, 1000); // this.count throws — this is undefined
// fixed — arrow function captures this class Timer { constructor() { this.count = 0; } tick = () => { this.count++; }; } const t = new Timer(); setTimeout(t.tick, 1000); // works — arrow fn has no own "this"
The analogy

A regular function's this is like a name tag handed out at check-in — it depends on who's checking you in (how it's called). An arrow function doesn't get its own name tag at all; it just reads whatever tag was already on the wall where it was defined (the enclosing scope's this), and never changes based on how it's later invoked. That's why arrow functions are the standard fix for callbacks that need to reference the surrounding class instance.

Microtasks vs. macrotasks

Promise callbacks (.then, async/await continuations, queueMicrotask) go on the microtask queue. Timer callbacks (setTimeout, setInterval) and things like I/O callbacks go on the macrotask (task) queue. After each single macrotask finishes, the event loop fully drains the entire microtask queue — including any new microtasks queued while draining — before it's allowed to pick up the next macrotask.

console.log('1'); setTimeout(() => console.log('2'), 0); Promise.resolve().then(() => console.log('3')); console.log('4'); // logs: 1, 4, 3, 2 // sync code first, then the microtask queue fully drains, then the timer

The practical impact: a Promise that resolves "immediately" will always run before a setTimeout(fn, 0) scheduled at the same moment, no matter how the code is ordered on the page. This trips people up in interviews specifically because both look like "run this as soon as possible" — but they're on different queues with a strict priority order between them.

Prototypes & prototypal inheritance
The analogy

The prototype chain is asking a question up a chain of managers when your own desk doesn't have the answer. Every object has an internal link to another object (its prototype). When you access a property, JavaScript checks the object itself first; if it's not there, it walks up to the prototype, then that prototype's prototype, and so on, until it finds the property or hits the end of the chain (null).

class syntax in modern JavaScript is largely sugar over this same mechanism — methods defined in a class body actually live on the class's prototype object, shared by every instance, rather than being copied onto each individual object. That's also why prototype-chain lookups are relevant to performance discussions: a property found on the object itself is faster to access than one several links up the chain, though this rarely matters outside of very hot code paths.

A frequent interview trap: forgetting that await only pauses execution within the current async function — it does not block the rest of the JavaScript engine. Other code, other requests, and other timers keep running normally while one function is paused on an await. This is the same non-blocking behavior the Node.js internals material covers at the runtime level — async/await is just a cleaner syntax on top of it.

Array methods that come up constantly
const nums = [1, 2, 3, 4, 5]; nums.map(n => n * 2); // [2,4,6,8,10] — transform each item, same length nums.filter(n => n % 2 === 0); // [2,4] — keep items matching a condition nums.reduce((sum, n) => sum + n, 0); // 15 — fold into a single value nums.find(n => n > 3); // 4 — first match, or undefined nums.some(n => n > 4); // true — does any item match? nums.every(n => n > 0); // true — do all items match?

map and filter both return new arrays and never mutate the original — that immutability is exactly why they're the default choice in React and other state-driven UIs, where mutating an array in place can silently break change detection. reduce is the most general of the bunch — map and filter can technically both be written as a reduce — but reaching for the more specific method when it fits is almost always more readable.

== vs. === vs. Object.is

== ("loose equality") coerces types before comparing — '5' == 5 is true. === ("strict equality") compares both value and type with no coercion — '5' === 5 is false. The near-universal convention is to default to === everywhere and treat =='s coercion rules as a source of surprising bugs rather than a convenience.

Even === has two well-known edge cases worth naming: NaN === NaN is false (NaN is defined to never equal anything, including itself — use Number.isNaN() to actually check for it), and -0 === 0 is true despite being distinct values. Object.is() is the rarely-used strict-equality variant that gets both of those "right" — Object.is(NaN, NaN) is true — but outside of niche cases like this, plain === is still what you reach for.

fetch() vs. axios

fetch() is the native, built-in way to make HTTP requests — no install required, available in every modern browser and in Node 18+. axios is a popular third-party library that wraps HTTP requests with a more batteries-included API. Both are promise-based, but they disagree on what counts as a "successful" request.

// fetch — the 404 is NOT rejected const res = await fetch('/api/thing'); // res.ok is false, but no error was thrown if (!res.ok) throw new Error(res.status); const data = await res.json(); // manual parse step
// axios — the 404 IS rejected try { const { data } = await axios.get('/api/thing'); // data is already parsed JSON } catch (err) { // non-2xx lands here automatically }

The single most common interview gotcha: fetch()'s promise only rejects on a genuine network-level failure (DNS failure, no connection, request aborted) — a 404 or 500 response is still a "successful" fetch as far as the promise is concerned, so you have to check response.ok yourself before trusting the body. axios auto-rejects on any non-2xx status, auto-parses JSON response bodies (no separate .json() call), and supports request/response interceptors — handy for things like attaching an auth token to every outgoing request in one place rather than repeating it per call site. The tradeoff is exactly what you'd expect: fetch costs nothing to use but requires more manual plumbing; axios costs a dependency but removes that plumbing.

Named exports vs. default exports
The analogy

A module is really just an object of exported bindings under the hood. export function Counter() {} puts a property literally named Counter on that object. A named export has to be imported by that exact name (in braces); a default export just fills one reserved slot — called default — on that same object, which is why it can be imported without braces and renamed freely on the way in.

// Counter.tsx export function Counter() { ... } // named export export default function Panel() { ... } // default export // importing it elsewhere import { Counter } from './Counter'; // must match the name, braces required import AnythingYouWant from './Counter'; // grabs .default, name is up to you // proving the "object of bindings" model directly: import * as mod from './Counter'; console.log(mod); // { Counter: [Function], default: [Function: Panel] }

A file can mix both — one default export plus any number of named exports alongside it. In practice, named exports tend to play nicer with tooling (auto-import, "find all usages," and rename-refactors all work more reliably when the name is fixed and searchable), which is part of why plenty of modern style guides — Vite's own React template included — lean toward named exports even for single-component files. What import * as mod actually returns isn't a plain object, either: it's a module namespace object — its prototype is null (hence [Module: null prototype] in Node's console output) and its properties are read-only, live bindings rather than copied values.

Interview-ready reasoning
What to say when this comes up

Naming these concepts under pressure

  • Closures: "a function keeps access to the variables from where it was defined, even after that outer scope has finished running" — then give the counter or loop-variable example.
  • this: "it's set by how the function is called, not where it's written" — and know that arrow functions are the fix when a callback needs to keep the surrounding this.
  • Microtasks vs. macrotasks: "Promises always drain before the next timer fires, even if both were scheduled at the same moment" — the classic console.log ordering question tests exactly this.
  • Prototypes: "classes are sugar over the same prototype-chain lookup mechanism" — shows you understand what class is actually doing underneath.
  • Default to === and be ready to name the NaN/-0 edge cases if pushed on equality specifically.
  • fetch vs. axios: "fetch only rejects on a network failure, not a 4xx/5xx — you have to check response.ok yourself" is the one fact worth having cold.
  • Named vs. default exports: "a module is really an object of bindings — named exports are keys matching their name, default export just fills one reserved default key" — the import * as mod trick is how you'd prove it live.
