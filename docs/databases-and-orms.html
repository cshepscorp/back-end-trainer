Databases & ORMs:
choosing the right tool

Why the parks app uses PostgreSQL over MongoDB, how relational data actually works, and what an ORM does for you.

The two broad categories
Document database

MongoDB

Stores data as JSON-like documents. No enforced schema — each document can have different fields. Fast reads for self-contained data. Best when data doesn't overlap much between records and structure varies. You manage relationships yourself.

Relational database

PostgreSQL

Stores data in structured tables with rows and columns. Relationships between tables are enforced by the database. A single source of truth for shared data. Best when data is interconnected, structured, and needs to stay consistent.

The analogy

MongoDB is like a filing cabinet full of folders. Each folder is self-contained — open it and everything you need is right there. But if two folders reference the same person, you've written their name in both. Update one, the other is out of date.

PostgreSQL is like a spreadsheet with tabs that reference each other. A person's name lives in one tab. Every other tab points to that row. Update the name once, everything that references it is immediately correct.

Relationship types — know these terms
One to many
User → Trips

One user owns many trips. Each trip belongs to exactly one user. Clear ownership on one side, multiple records on the other.

Many to many
Users ↔ Parks (favorites)

A user can favorite many parks. A park can be favorited by many users. Neither side owns the other. Requires a join table to connect them.

One to one
User → Profile

One user has exactly one profile. One profile belongs to exactly one user. Less common — often the data just gets merged into one table.

Why the join table exists

A trip contains many parks, and a park can appear in many trips — that's many-to-many. You can't store that cleanly in either the trips or parks table alone. The join table trip_parks sits between them and records each connection, plus the data that belongs to that connection specifically — like the stop order and drive time between stops.

What a join table row is actually saying

Take this saved trip: "Southwest Road Trip" with three stops in order — Zion → Bryce Canyon → Grand Canyon. In the database, that trip has id = 1, and those parks have id = 10, id = 11, id = 12.

Here's what the actual rows in trip_parks look like:

trip_id park_id stop_order drive_time_mins what this row is saying
1 10 1 null "Zion is stop #1 on the Southwest Road Trip — no drive time because it's the first stop."
1 11 2 90 "Bryce Canyon is stop #2 — 90 minutes from the previous stop."
1 12 3 215 "Grand Canyon is stop #3 — 215 minutes from the previous stop."
the key insight

The stop order and drive time don't belong to the trip, and they don't belong to the park. They belong to the relationship between them. Zion isn't always stop #1 — it's only stop #1 on this specific trip. A different user's trip might have Zion as stop #3. So that data has to live in the join table, not in either of the tables it connects.

What is an ORM?

Object-Relational Mapper

An ORM is a library that lets you talk to your database using JavaScript objects instead of raw SQL. It maps your database tables to JS classes, and rows in those tables to instances of those classes.

Think of it as a translator. Your database speaks SQL. Your application speaks JavaScript. The ORM sits between them and handles the translation both ways — turning your JS method calls into SQL queries, and turning SQL results back into JS objects you can work with.

Raw SQL vs ORM — same operation
Without an ORM — raw SQL
// Find all trips for a user const result = await db.query( `SELECT trips.*, users.name FROM trips JOIN users ON trips.user_id = users.id WHERE trips.user_id = $1 ORDER BY trips.created_at DESC`, [userId] ); const trips = result.rows; // Insert a new trip await db.query( `INSERT INTO trips (user_id, name) VALUES ($1, $2) RETURNING *`, [userId, 'Southwest Road Trip'] );
With Prisma (ORM) — JavaScript objects
// Find all trips for a user const trips = await prisma.trip.findMany({ where: { userId }, include: { user: true }, orderBy: { createdAt: 'desc' } }); // Insert a new trip await prisma.trip.create({ data: { userId, name: 'Southwest Road Trip' } });
ORM options for PostgreSQL + Node.js
Prisma
recommended for this project

Modern, type-safe, excellent developer experience. Auto-generates a schema from your models. Great docs. The best choice for a new Node.js + PostgreSQL project in 2025.

Drizzle
newer, very fast

Lightweight and TypeScript-native. Gaining popularity quickly. Less magic than Prisma — closer to writing SQL but with JS syntax. Good alternative worth knowing about.

Sequelize
older, widely used

The original Node.js ORM. Battle-tested and you'll see it in legacy codebases. More verbose and less modern than Prisma. You'll encounter it in interviews — worth recognizing.

Wait — didn't you mention Mongoose before?

Yes. Mongoose does for MongoDB roughly what Prisma does for PostgreSQL — it adds structure and a JS object interface on top of raw database calls. The term "ORM" technically applies to relational databases, so Mongoose is sometimes called an ODM (Object-Document Mapper) instead. But the concept is the same: a translator between your JS code and your database.

The decision — why PostgreSQL for the parks app
Interview-ready reasoning

PostgreSQL + Prisma

  • Park data is shared reference data — many users and trips point to the same parks. Storing it relationally means one source of truth, no duplication.
  • Real, meaningful relationships exist — users own trips, trips contain ordered parks, users favorite parks. PostgreSQL enforces these at the database level so your code doesn't have to.
  • Order and structure matter — trip stops have a sequence and drive times between them. A join table handles this cleanly without manual array management.
  • Many-to-many favorites — a join table is the correct and natural solution. Storing arrays of IDs in MongoDB documents is fragile and gets out of sync.
  • Prisma as the ORM — gives us type-safe queries, auto-generated schema, and a clean JS interface without writing raw SQL for every operation.
