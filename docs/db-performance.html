The N+1 query problem

An N+1 problem happens when your code runs one query to get a list, then loops over that list running one more query per item — N items means N extra queries, on top of the 1 you started with. It's the single most common performance bug in ORM-based code, because ORMs make it dangerously easy to write without noticing.

The analogy

Asking a librarian for a reading list, then walking back up to the desk separately for every single book on it. One trip to get the list, then N more trips — one per book — when you could have just asked for all N books while you were already standing there.

// N+1 — one query per trip, in a loop const trips = await prisma.trip.findMany(); for (const trip of trips) { // runs ONE MORE query, every single loop trip.parks = await prisma.park.findMany({ where: { tripId: trip.id } }); } // 1 query for trips + N queries for parks
101 queries for 100 trips
// Fixed — one query, joined upfront const trips = await prisma.trip.findMany({ include: { parks: true } }); // Prisma issues one query (or a small, // fixed number) and attaches parks to // each trip automatically
1 query, regardless of how many trips
Indexes — when they help, when they hurt
The analogy

A book's index vs. reading every page to find a topic. Without an index, the database does a "full table scan" — checking every row, like reading a whole book cover to cover to find one mention of a word. An index is a separate, sorted lookup structure that gets the database straight to the matching rows.

When indexes help

Columns used in WHERE clauses, JOIN conditions, and ORDER BY. A foreign key column (like user_id on a trips table) is a classic candidate — you're constantly filtering or joining on it.

When indexes hurt

Every index speeds up reads but slows down writes — each INSERT/UPDATE now has to update the index too, and indexes take disk space. Indexing every column "just in case" is a real anti-pattern.

How to actually check

Run EXPLAIN ANALYZE in front of a slow query in PostgreSQL. It shows whether the planner used an index scan or fell back to a sequential (full table) scan — the difference between "found the row instantly" and "checked every row to find it."

Transactions & ACID

A transaction groups multiple writes so they either all succeed or all fail together — no in-between state where only some of them happened. The classic example: transferring money between two accounts is two writes (debit one, credit the other) that must never happen partially.

A
Atomicity

All writes in the transaction succeed, or none of them do.

C
Consistency

The database moves from one valid state to another — constraints are never violated.

I
Isolation

Concurrent transactions don't see each other's half-finished work.

D
Durability

Once committed, the write survives a crash — it's actually on disk.

// Prisma transaction — both writes succeed or neither does await prisma.$transaction(async (tx) => { await tx.account.update({ where: { id: fromId }, data: { balance: { decrement: amount } } }); await tx.account.update({ where: { id: toId }, data: { balance: { increment: amount } } }); });

What to say when this comes up

Diagnosing a "slow endpoint" question

  • Check for N+1 first — it's the most common cause and the easiest to explain: are you looping over a list and querying per item?
  • Check if the WHERE/JOIN columns are indexed — if a query filters on a column with no index, that's often the next suspect.
  • Confirm writes that must stay consistent are wrapped in a transaction — especially anything touching money, inventory counts, or multi-table state.
  • Use EXPLAIN ANALYZE, don't guess — naming the actual diagnostic tool signals real experience, not just memorized theory.
