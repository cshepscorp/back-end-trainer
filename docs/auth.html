Authentication:
Sessions, JWTs & OAuth

How identity works on the web, why HTTP being stateless creates the problem, and the full auth stack the parks app uses.

The problem — HTTP is stateless

Every HTTP request is independent. The server has no memory of previous requests — each one arrives as if it's the first time. This means after you log in, the server immediately forgets you did. Every subsequent request needs to prove identity all over again.

Auth is the solution to this problem. The question is where that proof of identity lives between requests — on the server, or on the client.

Two approaches — sessions vs JWTs
Approach 1

Sessions

On login, the server creates a session, stores your user info in its own memory or database, and gives you back a random session ID. That ID gets saved in a cookie in your browser. Every subsequent request sends the cookie automatically — the server looks up the ID, finds your data, and knows who you are.

User data lives on the server. The browser only holds an ID — a claim ticket.

Approach 2

JWTs

On login, the server creates a JSON Web Token containing your user info directly — your ID, role, expiration time. It cryptographically signs it and sends it to you. Your client stores it. Every request you send the JWT, the server verifies the signature and reads your info right out of the token.

User data lives in the token, on the client. The server stores nothing.

The analogy

Sessions — the server holds your file in a cabinet, hands you a numbered ticket. Every visit you show the ticket and they pull your file.

JWTs — the server hands you your file directly, stamped and signed. Every visit you show the file and they verify the stamp. No cabinet needed.

Why JWTs for the parks app

Sessions work best when frontend and backend share the same server — cookies travel automatically on the same domain. But the parks app has a separate React frontend and Express backend running on different origins. Cookies across origins require careful CORS configuration and hit browser restrictions.

JWTs sidestep this entirely. The token is just a string — React stores it and manually attaches it to every request in an Authorization header. No domain matching required. Clean and explicit.

Where to store the JWT — and why it matters
Simpler approach — not chosen

localStorage

XSS vulnerable

Easy to implement — store the token after login, read it on every request, attach it to the Authorization header manually. Most tutorials use this approach.

The problem: localStorage is readable by any JavaScript running on the page. An XSS attack (malicious JS injected into your app) can read and steal the token. Once stolen, the attacker can impersonate the user until the token expires.

✓ what we're building

HttpOnly Cookie

XSS protected

The JWT is set as a cookie with the httpOnly flag. This means JavaScript on the page cannot read it — only the browser can send it. An XSS attack can't steal what it can't see.

Requires a bit more setup — credentials: 'include' on fetch calls and a CORS configuration that allows credentials. Worth it for a real deployed app.

The implementation difference
// ── EXPRESS SERVER — setting the HttpOnly cookie on login ── app.post('/auth/callback', async (req, res) => { const token = jwt.sign( { userId: user.id, email: user.email }, process.env.JWT_SECRET, { expiresIn: '1h' } ); res.cookie('token', token, { httpOnly: true, // JS can't read it secure: process.env.NODE_ENV === 'production', // HTTPS only in prod sameSite: 'strict', // your domain only maxAge: 60 * 60 * 1000 // 1 hour in ms }); res.json({ message: 'logged in' }); }); // ── REACT FRONTEND — no manual token handling needed ── const trips = await fetch('/api/trips', { credentials: 'include' // browser sends the cookie automatically }); // ── EXPRESS — CORS config to allow credentials ── app.use(cors({ origin: 'http://localhost:5173', // your Vite dev server credentials: true // allow cookies cross-origin }));
HttpOnly cookie setup — Express sets it, browser sends it, JS never touches it
Interview answer — JWT storage trade-off
"I could have stored the JWT in localStorage — it's simpler and how most tutorials show it. But localStorage is vulnerable to XSS attacks, so I went with HttpOnly cookies instead. JavaScript on the page can't read them, which removes that attack surface entirely. It required a bit more setup on the CORS configuration, but for a real deployed app it's the right call."
OAuth — delegating authentication to Google
The user-facing reason

No new password

Users sign in with a Google account they already have. No new username, no new password to remember, no forgot-password flow to build.

The developer-facing reason

Passwords are a liability

Handling passwords means hashing, storage, breach risk, and reset flows. OAuth lets you say: "Google handles that. I'll trust their confirmation." You never touch the password.

The OAuth flow — step by step
1
User clicks "Sign in with Google"
Your React app redirects the user to Google's login page. Your app is completely out of the picture at this point.
2
User logs in with Google
Google handles authentication entirely. Your app never sees the password.
3
Google redirects back with a temporary code
Google sends the user back to your Express server with a short-lived authorization code. This code is useless on its own.
4
Your server exchanges the code for user info
Express sends the code to Google's API server-to-server. Google responds with the user's name, email, and Google ID. This exchange happens on the backend — never in the browser.
5
Your server finds or creates the user
Look up the Google ID in your users table. If they exist, fetch them. If not, create a new user row. First-time login creates the account automatically.
6
Your server issues a JWT and sets the HttpOnly cookie
Your server mints a JWT with the user's ID and sets it as an HttpOnly cookie. Google is now completely out of the picture — all future requests use this JWT.
7
All future requests use the JWT
The browser sends the cookie automatically on every request. Express verifies the JWT and identifies the user. Normal app flow resumes.
The library — Passport.js

Passport.js is the standard Node.js library for OAuth. It has "strategies" for dozens of providers — Google, GitHub, Apple, and more. For the parks app you'd use passport-google-oauth20. Passport handles the redirect, the code exchange, and the callback — you just configure your Google credentials and tell it what to do with the user info it retrieves.

The full auth stack — parks app
Interview-ready reasoning

OAuth → JWT → HttpOnly Cookie

  • OAuth via Google — no passwords to handle, low friction for users, delegates auth to a trusted provider.
  • JWTs over sessions — the frontend and backend are separate projects on different origins. JWTs are stateless and travel explicitly in requests, avoiding the cookie/CORS complexity that sessions bring in a decoupled architecture.
  • HttpOnly cookies over localStorage — removes the XSS attack surface entirely. JavaScript on the page cannot read the token. Slightly more setup on CORS, worth it for a real deployed app.
  • Passport.js — handles the OAuth flow so we're not implementing the Google redirect and code exchange from scratch.
