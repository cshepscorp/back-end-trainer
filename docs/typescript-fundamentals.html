TypeScript fundamentals

A small, growing set of TypeScript-specific concepts — starting with generics, the feature that looks like syntax noise until you see exactly what problem it solves.

Generics (<T>)
The analogy

A generic function is a shipping label template with a blank "contents" field. The box handles the packing and shipping logic identically no matter what's inside — but it still writes down, precisely, what's actually in this particular box, so nobody down the line has to guess or unwrap it to find out. any would be leaving that field permanently blank: the box still ships, but nobody downstream knows what's safe to assume about what's inside until they open it.

<T> is a placeholder for a type, the same way a function parameter is a placeholder for a value. Regular parameters let you write one function that works for many different values; generics let you write one function that works for many different types, while TypeScript still tracks exactly which type you used each time — so you keep type safety instead of giving it up.

// Hardcoded — reusable for nothing else function useDebounce(value: string, delayMs: number): string { // ... }
// any — reusable, but no type safety left function useDebounce(value: any, delayMs: number): any { // ... }

Hardcoding a type (e.g. string) works fine for one call site — a search box — but makes the hook useless for debouncing a number, an object, anything else; you'd copy-paste the whole hook per type, defeating the point of extracting reusable logic. Reaching for any instead "works" for every type, but TypeScript stops checking anything — the result comes back typed any, so nothing warns you if you treat it as the wrong shape later. You've made it reusable, but thrown away the safety net that's the reason you're using TypeScript at all.

// Generic — reusable AND still type-checked function useDebounce<T>(value: T, delayMs: number): T { const [debouncedValue, setDebouncedValue] = useState(value); useEffect(() => { const timeoutId = setTimeout(() => setDebouncedValue(value), delayMs); return () => clearTimeout(timeoutId); }, [value, delayMs]); return debouncedValue; }

<T> declares "this function has a type variable named T, and I don't know what it is yet — whoever calls this function will tell me, based on what they actually pass in." T then gets reused everywhere it needs to line up: the value parameter is T, useState(value) therefore holds a T, and the return type is declared T too — so TypeScript can guarantee "whatever type you put in is exactly the type you get back."

const debouncedSearch = useDebounce('hello', 300); // T = string here, debouncedSearch is typed `string` const debouncedCount = useDebounce(42, 300); // T = number here, debouncedCount is typed `number` const debouncedFilters = useDebounce({ category: 'sales' }, 300); // T = { category: string } here, keeps that exact shape

You never actually have to write useDebounce<string>('hello', 300) yourself in normal use — TypeScript looks at what you passed as value and figures out T automatically. That's type inference, and it's why generics don't feel as clunky in practice as the <T> syntax suggests at first glance. The exact same pattern shows up anywhere a hook or function needs to stay reusable across shapes while still being precisely typed — e.g. a useFetch<T> hook, where useFetch<DataRecord[]>('/api/data') tells TypeScript exactly what the resolved data will look like, rather than everyone getting back an untyped blob.

Interview-ready reasoning
What to say when this comes up

Naming this concept under pressure

  • Generics: "a placeholder for a type, the same way a parameter is a placeholder for a value — lets one function stay reusable across types without giving up type-checking, unlike `any`." Be ready to explain why hardcoding a type and using `any` both fail the reusable-and-safe bar that generics clear.
