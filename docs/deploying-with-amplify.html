Case study · Cloud deployment

Deploying to the cloud, start to finish

A record of actually standing up a serverless app on AWS — not the theory, the real sequence of decisions, the bugs, and how each one got diagnosed. This is the "tell me about a time you debugged a production issue" story, already written down.

What we were building

A daily automated quiz companion to quiz.html: a scheduled job picks a not-yet-mastered topic every morning, emails a notification, and a small web app lets you take that quiz and track progress — completely separate from the self-guided quiz's local browser storage. The point of building it wasn't just the quiz itself; it was going through a real, small, end-to-end cloud deployment, which is exactly the kind of practical experience that's easy to talk around in an interview and much stronger to have actually done once.

Infrastructure as code, in practice
The analogy

Writing the backend in code is handing an architect's blueprint to a contractor, instead of building the house yourself brick by brick. AWS Amplify (built on AWS CDK) took our TypeScript resource definitions — a data schema, a function, a schedule — and figured out the actual build order itself: what needs to exist before what, what permissions to wire up, what to tear down if something's removed. We never ran a single manual "create this table" or "attach this permission" command.

Concretely, one npx ampx sandbox deploy created: three DynamoDB tables (Question, Progress, DailyQuiz), an AppSync GraphQL API in front of them with auto-generated resolvers, an IAM role scoping exactly what the function could touch, the Lambda function itself, an EventBridge Scheduler rule to trigger it every morning, and an API key for the frontend to authenticate with. Standing up the AppSync layer plus tables is usually the single slowest part of a first deploy — often several minutes — even though every deploy after that is much faster, since the tool only touches what actually changed.

What a Lambda actually is
The analogy

A normal event handler runs inside a process you're already keeping alive — your Node server, the browser. A Lambda has no persistent process at all. AWS spins up a temporary execution environment only at the moment it's triggered, runs the handler code in it, and tears it back down afterward. You're billed for the milliseconds it actually executed, not for a server idling the rest of the day waiting. That's exactly why it fit "email me once every morning" — rather than running a whole server 24/7 to fire one job a day, EventBridge's schedule invokes the function once, it runs for a couple of seconds, and then nothing exists again until tomorrow.

The bug: two ways to grant access, only one wires up the client

The function needed to read and write the Data models. There are two ways to grant a function that kind of access in Amplify Gen 2, and they look almost interchangeable — but only one of them actually works with the documented Data-client pattern.

// ✗ backend.ts — manual IAM grant // Gives the Lambda IAM permission to call // AppSync directly, but doesn't register the // function as a "data-access" function — // so $amplify/env/<name> never gets generated. backend.data.resources.graphqlApi .grantQuery(fn.resources.lambda); backend.data.resources.graphqlApi .grantMutation(fn.resources.lambda);
Correct permissions, wrong mechanism
// ✓ data/resource.ts — schema-level grant const schema = a.schema({ /* models */ }) .authorization(allow => [ allow.resource(dailyQuizGenerator) ]); // This is what triggers Amplify's build // tooling to generate the env module AND // wire up getAmplifyDataClientConfig() correctly.
Same permissions, plus the generated wiring
Symptom 1

Deploy failed with "Could not resolve $amplify/env/daily-quiz-generator" — an esbuild error while bundling the function.

Workaround (wrong turn)

Swapped the generated env import for plain process.env, since the values are real Lambda environment variables either way. Deploy succeeded.

Symptom 2

Running the function threw "The data environment variables are malformed" from inside getAmplifyDataClientConfig() — AMPLIFY_SSM_ENV_CONFIG in the dumped environment was just {}.

Root cause, found via AWS's own docs

Amplify's official "Grant Lambda function access to API and Data" page showed the missing piece: function access has to be declared on the schema object itself via allow.resource() — that's what actually triggers the generated env module and the S3-bucket-backed schema config the client reads at runtime. The manual grantQuery/grantMutation calls gave equivalent IAM permissions but skipped that registration step entirely.

Fix

Moved the grant to the schema (left code block above), removed the manual IAM grant, restored the generated env import. Deploy and function both succeeded on the next try.

The lesson generalizes past Amplify: two APIs that produce the same permissions aren't necessarily the same mechanism. One was a low-level IAM primitive; the other was a framework-level convention with side effects (code generation) the low-level version doesn't know to trigger. When a "should be equivalent" swap breaks something unrelated, the framework's own docs for the exact feature — not Stack Overflow, not GitHub issue threads — is usually where the actual contract is spelled out.

AWS credentials & a near-miss
Access keys vs. SSO

AWS pushes you toward IAM Identity Center (SSO) with a warning banner every time you create an access key. For a solo developer deploying from their own machine, a long-lived access key is still the standard, simplest path — SSO requires organization-level setup that's real overhead for a personal project. The warning is generic, not a signal something's wrong with this use case specifically.

The near-miss

The CSV file AWS lets you download when you create an access key — containing the actual secret in plain text — ended up sitting untracked in the project folder. Had it been swept up by a broad git add . and pushed, that would have published a live AWS secret to GitHub. Caught before it happened by reviewing git status before staging, rather than staging everything reflexively.

The habit worth keeping: stage deliberately (git add <specific paths>, not git add -A) on any repo that isn't brand new, and add a .gitignore entry for credential file patterns (*accessKeys*.csv, .env) before you ever need it — not after.

Email delivery: SES sandbox mode & the spam folder

Amazon SES starts every new account in "sandbox mode" — it can only send to and from addresses you've explicitly verified, until you request production access. Since this notification only ever sends to the same address it sends from, sandbox mode was actually sufficient forever — no need to leave it for a single-recipient use case.

The first email landed in spam — not an SES misconfiguration, but Gmail flagging a structural mismatch: a message claiming to be "from" your own address that actually arrived via a third party's mail servers instead of Google's. That pattern (nobody normally emails themselves through an external relay) is a classic spam signal regardless of content. Marking it "Not spam" once trains the filter for that sender going forward.

From personal sandbox to a real deployment

npx ampx sandbox is a real, deployed AWS environment — but it's tied to a developer's own machine and credentials, and meant to be torn down when you're not actively iterating. It's the wrong thing to leave running unattended as the actual production version. The persistent version comes from connecting the git repo to Amplify Hosting, which deploys from CI on every push, independent of anyone's laptop being on.

Monorepo app root

The Amplify project lived in a subfolder of a larger repo (alongside this static site), not at the repo root. Amplify Hosting's monorepo setting tells the build which subfolder is the actual app — otherwise it can't find the backend definition or run the right build commands.

npm ci vs. npm install

CI environments use npm ci, which requires package.json and package-lock.json to match exactly — unlike npm install, it won't quietly resolve small drift between them. A lock file that had gotten slightly out of sync (from installing dependencies in stages locally) failed the very first CI build until npm install was re-run locally and the refreshed lock file was committed.

Interview-ready reasoning
What to say when this comes up

"Tell me about a time you debugged something in production" / "Walk me through deploying a service"

  • Name the actual symptom before the fix — "the deploy failed with an unresolvable module error, then the function itself threw a malformed-config error" reads as someone who watched the failure closely, not someone reciting a solution.
  • Two APIs granting the same permission aren't always the same mechanism — the manual IAM grant and the schema-level grant produced identical access but only one triggered required code generation. Worth having as a go-to example of "looked equivalent, wasn't."
  • When docs and community threads disagree, the framework's own current docs for that exact feature win — GitHub issues are often outdated or describe a different version's behavior.
  • Security hygiene is a habit, not a one-time check — reviewing git status before staging is what caught a live credential before it reached a remote repo, not a special audit step.
  • "Deployed" has degrees — a personal sandbox, a CI-deployed branch, and a production environment with monitoring are three different levels of "done," and knowing which one you're actually at matters.
