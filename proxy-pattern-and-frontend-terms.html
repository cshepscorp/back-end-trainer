NPS API
api.nps.gov
① Browser → Server

User types a search. React sends a fetch() to your server. No API key needed — the browser doesn't know the NPS API exists.

② Server → NPS API

Your Express server receives the request, attaches the secret API key, and forwards the request to api.nps.gov.

③ NPS processes

NPS validates the key, queries their database, and prepares a JSON response of matching parks.

④ NPS → Server

Park data returns to your server. Here you can filter, transform, or cache the response before passing it on.

⑤ Server → Browser

Your server sends the clean response to the browser. React receives it and renders the park cards.

With a proxy server ✓

API key stays secret

The key lives in an environment variable on your server. It never touches the browser. Even if someone opens dev tools, they can't find it.

Without a proxy ✗

Key is exposed

If the browser calls the NPS API directly, the key has to exist in your JavaScript — visible to anyone who opens the Network tab or reads your source code.

// ✗ DON'T — key exposed in browser JS const res = await fetch( `https://api.nps.gov/api/v1/parks?q=${query}&api_key=ABC123SECRET` ); // ✓ DO — browser calls YOUR server, key stays hidden const res = await fetch(`/api/parks?q=${query}`); // On your Express server (key is safe here) app.get('/api/parks', async (req, res) => { const npsRes = await fetch( `https://api.nps.gov/api/v1/parks?q=${req.query.q}&api_key=${process.env.NPS_API_KEY}` ); const data = await npsRes.json(); res.json(data); });

Frontend terminology — plain English
UI frameworks / libraries — what you build your interface with
UI library
aka "frontend library"
A collection of tools for building user interfaces. Handles how components render, update, and react to data changes. Does not decide routing, data fetching, or project structure — you wire those up yourself.
React Solid Preact
UI framework
aka "frontend framework"
Like a library but more opinionated. Comes with built-in conventions for routing, state management, and project structure. More decisions made for you — less flexibility, faster start.
Vue Angular Svelte
React specifically
library, not a framework
React only handles the UI layer — it's technically a library. You choose your own router (React Router), data fetching, etc. This is why meta-frameworks exist on top of it.
Most widely used ~40% of devs
Meta-frameworks — what you use to structure a full application
Meta-framework
aka "app framework" or "full-stack framework"
Sits on top of a UI library and adds everything it's missing: file-based routing, server-side rendering, API routes, build optimization, deployment config. Turns a library into a complete application structure.
Next.js Remix Nuxt SvelteKit
Next.js
React meta-framework
The most popular meta-framework for React. Adds file-based routing, server-side rendering (SSR), static generation, image optimization, and API routes. Built and maintained by Vercel.
React + routing + SSR
Vite
build tool — not a framework
A fast build tool and dev server. It compiles and bundles your code. It is not a meta-framework — it has no opinions about routing or rendering. Think of it as the engine room, not the application.
Build tool only replaces webpack
Rendering strategies — how and where your HTML gets generated
CSR
Client-side rendering
The server sends a nearly empty HTML file. The browser downloads your JS, runs it, and builds the UI. Fast after initial load, but slow first paint. What plain React + Vite does by default.
Vite + React Create React App
SSR
Server-side rendering
The server generates full HTML for each request and sends it to the browser. Faster first paint, better SEO. The browser then "hydrates" the HTML with React so it becomes interactive.
Next.js Remix
SSG
Static site generation
HTML is generated once at build time, not per request. Blazing fast, great for content that doesn't change often. Not great for dynamic, user-specific data like saved trips.
Next.js Astro Gatsby
What this means for the parks app
The decision

React + Vite vs Next.js

The parks app is dynamic and user-specific — saved trips, auth, real-time search. SSG is out. The choice is between a simple CSR setup or a meta-framework. Here's how they stack up:

React + Vite
Simple, fast to set up, you control everything. CSR only — the server sends an empty shell, React builds the UI in the browser. You manage routing yourself (React Router). Good for SPAs.
Next.js recommended
Adds file-based routing, SSR for fast page loads, and API routes (so your Express proxy can live right inside the project). More conventions but less glue code to write.
Plain React + separate Express
Two separate projects — a React frontend and an Express backend. More control, cleaner separation, but more configuration. Good for learning how the layers interact independently.

For this project, either Next.js or React + separate Express are valid. Next.js is faster to ship. Separate React + Express teaches you more about how the layers connect — which matters for interviews. Worth discussing before deciding.
