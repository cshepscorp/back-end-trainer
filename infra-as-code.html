Infrastructure as code & deployment basics

The vocabulary and mental models behind "how does this actually get deployed" — declarative vs. imperative infrastructure, what a tool like CloudFormation or Terraform actually does with your config, serverless vs. always-on trade-offs, and IAM as the permission layer underneath all of it.

Looking for the specific story of how this project got deployed to AWS Amplify — the bugs, the fixes, the actual commands? That's a separate case study: Deploying to the cloud, start to finish. This page is the general concepts; that one is what actually happened.
Declarative vs. imperative infrastructure
The analogy

Imperative is a recipe; declarative is a finished-dish photo. An imperative approach is a script of exact steps — "create this VM, then install this package, then open this port, then start this process" — run in order. A declarative approach just describes the end state you want — "I want one server, this size, running this app, with this port open" — and hands that description to a tool that figures out what steps are needed to make reality match it.

// imperative — a script of steps ssh server apt install postgres createdb myapp export PORT=3000 npm start & // run it twice? results may differ // depending on current server state
// declarative — describe the end state database: engine: postgres service: port: 3000 command: npm start // run it 10 times — tool computes the // diff from current state each time

Infrastructure-as-code tools (Terraform, AWS CloudFormation, Pulumi, and Amplify's CDK-based config underneath) are declarative. The practical benefit is idempotency — running the same declarative config twice doesn't recreate everything from scratch or double up resources; the tool compares the description against what's actually deployed and only changes what's different. An imperative script re-run against an already-configured server has no such guarantee — it might error out, duplicate work, or silently drift depending on what state the server happened to be in.

What an IaC tool does with your config: dependency graphs
The analogy

An IaC tool reads your infrastructure description the way a project manager reads a construction plan — building a dependency graph before doing anything. You don't hand a contractor a photo of a finished house and have them start randomly; you can't put up drywall before the framing exists. The tool inspects everything you declared — a database, a function that reads from it, permissions the function needs — figures out what depends on what, and works out a valid build order automatically.

Concretely: if your config declares a Lambda function that reads from a DynamoDB table, the tool sees that dependency and knows the table has to exist (or at least be far enough along) before the function's permissions can reference it. You never write out that ordering yourself — you just declare both resources and how they relate, and the tool derives the graph and executes accordingly, in parallel wherever there's no dependency forcing a specific order.

This is also what makes changes safe to reason about: before actually applying anything, most of these tools can show you a "plan" or "diff" — here's what would be created, changed, or destroyed, based on comparing your new config against the last known deployed state. Reviewing that plan before approving it is the infrastructure equivalent of reviewing a code diff before merging.

Serverless vs. always-on servers
ConsiderationServerless (e.g. Lambda)Always-on (e.g. a VM or container running 24/7)
What's runningNothing, most of the time — code only executes when triggered, then the environment goes awayA process stays alive continuously, whether or not it's currently handling a request
Cost modelPay per invocation/execution time — near-zero cost at zero trafficPay for the server running, regardless of traffic level
Cold startsA request after idle time may wait briefly while the environment spins upNo cold start — the process is already warm and waiting
Good forSpiky, unpredictable, or infrequent traffic; scheduled/event-driven jobsSteady, predictable, high-frequency traffic where cold starts would be costly
State between requestsNone guaranteed — treat each invocation as if it might be a fresh environmentIn-memory state can persist across requests naturally (with the multi-instance caveats system design covers)

This is exactly the trade-off behind why a scheduled daily task (like a cron job that runs once and does a bounded amount of work) is a natural fit for a serverless function, while a server handling a constant stream of live user traffic often favors an always-on process — the "pay only when it runs" model stops being an advantage once something is effectively always running anyway.

IAM: the permission layer underneath everything
The analogy

IAM (Identity and Access Management) roles are like key cards, not passwords. A person doesn't get a copy of a database's actual credentials; a piece of infrastructure (a function, a server) is issued a role — a key card — that's been granted access to specific doors (specific resources, specific actions on them). The system checks the key card at the door every time, rather than the requester needing to know a secret to get in.

This matters architecturally because it replaces "hand out a secret and hope it's stored safely" with "grant a role specific, narrow permissions, enforced by the platform itself." A Lambda function with a role that can only read from one specific table can't accidentally (or maliciously, if compromised) write to a different one, delete a bucket, or spin up new infrastructure — the permission boundary is enforced independent of the function's own code.

The principle to name in an interview is least privilege: grant only the specific permissions a piece of infrastructure actually needs to do its job, nothing broader "just in case." A role that can do everything is a much bigger blast radius if something goes wrong — a bug, a leaked credential, a misconfigured request — than a role scoped tightly to exactly what's required.

Environments & promotion

Most real deployments aren't a single environment — there's typically a personal/dev environment (a sandbox one engineer can freely break), a shared staging environment (closer to production, used to catch integration issues before real users see them), and production itself. Infrastructure as code makes this practical: the same declarative config can be applied to multiple environments with different parameters (a smaller database in dev, stricter alerting in production) instead of hand-building each environment separately and hoping they stay in sync.

Promotion is the practice of moving a change through these environments in order — verified in dev, then staging, then production — rather than deploying straight to production. It's the infrastructure equivalent of a code review process: each stage is a chance to catch a problem before it reaches real users, and the cost of a mistake increases the further along that chain it slips through undetected.

Rollback & drift

Because declarative IaC tools track the last known deployed state, a bad deploy can often be rolled back by reapplying the previous known-good configuration — the tool computes the diff back to that state the same way it computes any other change. This is a real advantage over ad hoc manual changes, where "undo" often means someone trying to remember and manually reverse whatever they clicked or typed.

Drift is what happens when the real infrastructure no longer matches what the IaC config says it should be — usually because someone made a manual change directly (clicking around in a cloud console) instead of going through the declarative config. Drift is a genuine operational risk: the next time the IaC tool runs, it may "correct" that manual change back to what the config says, silently undoing something someone did for a real reason. The standard discipline is to treat the IaC config as the single source of truth and avoid manual out-of-band changes to anything it manages.

Interview-ready reasoning
What to say when this comes up

"Walk me through how you'd deploy this"

  • Lead with declarative over imperative — describe the desired end state and let a tool compute the diff, rather than scripting exact steps that may not be safe to re-run.
  • Name the dependency graph — the tool figures out build order from what you declare (a function needing a database) rather than you hand-sequencing every step.
  • Justify serverless vs. always-on by traffic shape — spiky/infrequent leans serverless, steady/high-frequency leans always-on, and say why cold starts matter for one but not the other.
  • Default to least-privilege IAM roles — narrow, resource-specific permissions rather than broad access "just in case."
  • Mention promotion through environments — dev → staging → production, catching problems before they reach real users, rather than deploying straight to production.
