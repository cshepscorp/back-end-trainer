System design basics

Where "how does your app work" turns into "how would this scale" — caching, load balancing, message queues, and the trade-off every system design question circles back to.

Vertical vs. horizontal scaling
The analogy

Vertical scaling is buying a bigger truck. Horizontal scaling is buying more trucks. A bigger truck (more CPU/RAM on one server) is simple but has a ceiling and a single point of failure. More trucks (more servers sharing the load) has no real ceiling, but now you need a way to direct traffic to the right truck — a load balancer.

Vertical scaling

Add more power to one machine. Simple, no coordination needed — but there's a hardware ceiling, and that one machine is a single point of failure.

Horizontal scaling

Add more machines running the same app. Scales much further and survives one instance dying — but now requires a load balancer and, often, shared state (sessions, cache) accessible to every instance.

Load balancing

A load balancer sits in front of multiple server instances and decides which one handles each incoming request — commonly by round robin (rotate through instances in order) or least connections (send to whichever instance is currently least busy). This is exactly why horizontal scaling requires stateless authentication (like JWTs) or a shared session store — any instance might handle any request.

Caching layers
In-memory cache (Redis)

An extremely fast key-value store, usually in RAM, sitting in front of your database. Great for data that's expensive to compute or query but doesn't need to be perfectly fresh every millisecond.

CDN

Caches static assets (images, JS bundles) at servers physically closer to the user, so requests don't have to round-trip to your origin server at all.

The hard part isn't caching — it's invalidation

A cache is only useful if it's correct. The recurring challenge is knowing when to clear or update a cached value once the underlying data changes — the same cache invalidation problem already covered for the proxy pattern, just at a bigger scale.

Message queues & background jobs
The analogy

A to-do list a separate worker chips away at, instead of making the customer wait at the counter while you do the work. When a request triggers something slow — sending an email, resizing an image, generating a report — you drop a job onto a queue and respond to the user immediately. A separate worker process picks jobs off the queue and handles them independently.

Popular tools: BullMQ (Redis-backed, common in Node apps), RabbitMQ, and cloud-managed options like AWS SQS. The point isn't memorizing a specific tool — it's recognizing when work should be decoupled from the request/response cycle.

CAP theorem — the trade-off, briefly

When a network partition happens (part of your distributed system can't talk to another part), you have to choose: stay Consistent (refuse requests until both sides agree) or stay Available (keep serving requests, accepting they might briefly disagree). You can't fully have both during the partition — Partition tolerance is a given for any distributed system, so in practice this is really a C-vs-A trade-off during failures, not three equal options.

Interview-ready reasoning
What to say when this comes up

"How would you scale this to a million users?"

  • Start with what's actually slow — don't reach for microservices or Redis before establishing where the bottleneck is.
  • Cache what's expensive and doesn't change often — and say out loud how you'd invalidate it.
  • Move slow work off the request path — queues for anything that doesn't need to finish before you respond.
  • Scale horizontally, and say what that requires — stateless auth, a load balancer, shared cache/session storage.
  • Only bring up microservices if complexity or team size actually justifies it — naming the trade-off matters more than naming the buzzword.
