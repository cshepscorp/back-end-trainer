AI / LLM fundamentals

The vocabulary that shows up the moment "how would you add AI to this" comes up in an interview — what these systems actually do, where they break, and the handful of patterns (RAG, agents, evals) that separate a real integration from a demo.

What an LLM actually does
The analogy

An LLM is autocomplete that read the entire internet. At its core, it's a next-token predictor — given everything so far, what's the statistically most plausible next chunk of text? There's no internal database of facts it "looks up" and no built-in understanding of truth. Everything it produces, correct or not, comes from the same mechanism: predicting plausible continuations based on patterns learned during training.

This single fact explains a lot of LLM behavior that otherwise seems strange: why they can write fluent, confident-sounding text about things that never happened (there's no separate "is this true" check baked into the generation process), why longer, more specific prompts tend to produce better results (more context narrows down what a plausible continuation looks like), and why the same prompt can produce different answers on different runs (the model samples from a distribution of likely next tokens rather than deterministically retrieving one fixed answer).

The context window
The analogy

The context window is short-term working memory, not long-term storage — a desk, not a filing cabinet. Everything the model can "see" while generating a response — your prompt, the conversation so far, any documents you've pasted in — has to fit on that desk at once. Once a conversation exceeds the window, the oldest material falls off the edge; the model has no memory of it unless it's explicitly re-included.

This is also why the model has zero persistent memory between separate conversations by default — each new conversation is a completely clean desk. Anything that needs to carry over (a user's preferences, prior decisions) has to be re-supplied as part of the context on each new request, which is exactly the problem retrieval systems (below) are built to solve at scale.

Prompting vs. fine-tuning
ConsiderationPromptingFine-tuning
What it isGiving the existing model better instructions and examples at request timeContinuing to train the model's own weights on your specific data
Setup costLow — edit a string, redeploy instantlyHigh — needs a training dataset, compute, and a retraining pipeline
Good forFormat, tone, following instructions, most day-to-day use casesTeaching genuinely new behavior or a very specific style at scale
Where new facts should goRetrieval (RAG) — inject them into the promptRarely the right tool for new facts; they get diluted and go stale

The default assumption should be prompting, not fine-tuning. Fine-tuning is a real tool, but it's the expensive, slow option — most product problems that seem to call for it ("the model doesn't know about our data") are actually retrieval problems, solved far more cheaply by handing the model the relevant facts at request time instead of trying to bake them permanently into its weights.

Retrieval-augmented generation (RAG) & embeddings
The analogy

RAG is an open-book exam instead of one from memory. Rather than expecting the model to have memorized your specific documents (it hasn't — it was trained on a general internet snapshot, not your company's docs), you find the most relevant few paragraphs and hand them to the model as part of the prompt, right before asking the question. The model still does the reasoning and writing; it just isn't working from memory alone.

Finding "the most relevant paragraphs" is what embeddings are for: a separate model converts text into a vector (a long list of numbers) positioned so that texts with similar meaning end up close together in that space — a bit like GPS coordinates for meaning instead of location. To answer a question, you embed the question, then search a vector database for the stored document chunks whose embeddings are closest to it, and those chunks become the "open book" pages you hand to the LLM.

The practical pipeline: split your source documents into chunks → embed each chunk once, ahead of time → store the embeddings in a vector database → at query time, embed the incoming question, retrieve the nearest chunks, and stuff them into the prompt alongside the question. The retrieval step is a classic search problem; the LLM is only responsible for the last step of actually answering using what it was handed.

Hallucination — why it happens, and what actually reduces it

Given the "statistically plausible next token" mechanism above, hallucination isn't really a bug in the traditional sense — it's the same generation process producing a confident, fluent, and false continuation, because nothing in that process distinguishes "true and well-supported" from "sounds right." It happens most when a model is asked about something specific it wasn't trained on well enough, or something outside its training data entirely (recent events, your internal company data, obscure specifics).

What actually helps: grounding the model in real source material via RAG (so it's summarizing/quoting supplied text rather than recalling from memory), asking it to cite which supplied passage supports each claim, and lowering "temperature" (the randomness setting) for factual tasks. What doesn't reliably help: just asking the model to "be accurate" or "don't make things up" in the prompt — that's an instruction about output style, not a change to the underlying mechanism that produces the error.

Agents & tool use
The analogy

Tool use is giving the model a calculator instead of asking it to do long division from memory. LLMs are unreliable at precise arithmetic, real-time facts, and taking real actions (sending an email, querying a database) — all things a plain function call handles perfectly. "Tool use" means the model can, mid-response, request that your code run a specific function with specific arguments, see the real result, and incorporate that result into its answer instead of guessing.

An agent is this pattern looped: the model plans a step, calls a tool, observes the result, decides the next step, and repeats — rather than answering in one shot. This is what powers things like "search the web, then summarize" or "check the database, then reply" workflows. The trade-off is real: more steps means more latency, more cost, and more places for something to go wrong, so agentic loops are worth reaching for when a task genuinely needs multiple dependent steps, not by default.

Evals — testing something non-deterministic

Normal unit tests assert an exact expected output. LLM output varies run to run, so "does the output exactly equal X" mostly doesn't work. Evals are the equivalent testing discipline for AI features: a fixed set of representative inputs, paired with a way to score whether each output meets the bar — a rule-based check (does it contain required fields, is it valid JSON), a human rubric, or another LLM call acting as a judge against defined criteria.

The interview-relevant point: shipping an AI feature without any evals is shipping without tests — it might work great on the three examples you tried by hand and fail silently on inputs you didn't think to check. A small eval set that runs on every change is the AI-feature equivalent of a regression test suite.

Interview-ready reasoning
What to say when this comes up

"How would you add AI to this feature?"

  • Start with prompting, not fine-tuning — cheaper, faster to iterate, and covers most real use cases.
  • If the model needs to know your specific data, that's a retrieval problem — describe RAG rather than assuming the model already "knows" your content or needs retraining to learn it.
  • Reach for tool use/agents only when a task genuinely needs real actions or multi-step reasoning — not as a default architecture, since every extra step adds latency, cost, and failure surface.
  • Say out loud how you'd catch hallucination — grounding in real sources, citations back to source passages, and lower temperature for factual tasks.
  • Mention evals — testing an AI feature isn't the same as testing deterministic code, and naming that distinction (rather than ignoring it) reads as someone who's actually shipped one of these before.
