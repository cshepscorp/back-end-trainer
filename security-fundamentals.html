Security · Beyond auth

Security fundamentals,
beyond auth

You've already got sessions, JWTs, and OAuth covered. This is the rest of the standard security checklist — input validation, injection attacks, CSRF, and rate limiting.

Input validation — never trust the client

Anything arriving from outside your server — request bodies, query params, headers — should be treated as untrusted until validated. A library like Zod or Joi lets you define a schema once and reject malformed data before it ever touches your business logic or database.

// Validate at the boundary, before anything else runs const schema = z.object({ email: z.string().email(), age: z.number().int().positive() }); app.post('/users', (req, res) => { const result = schema.safeParse(req.body); if (!result.success) { return res.status(400).json({ error: 'Invalid input' }); } // result.data is now safe to use });
Reject bad data before it reaches your logic — not after
SQL injection
The core problem

If user input gets pasted directly into a SQL string, a malicious user can write input that changes the query itself — not just the data inside it. Classic example: a login form where the "password" field contains SQL that always evaluates true.

// ✗ Vulnerable — string concatenation const query = `SELECT * FROM users WHERE email = '${email}'`; // email = "' OR '1'='1" breaks out // of the string and changes the query
User input becomes part of the SQL itself
// ✓ Safe — parameterized query const result = await db.query( 'SELECT * FROM users WHERE email = $1', [email] ); // email is always treated as DATA, // never as part of the query structure
Parameters are data, never executable SQL
// Normal input: email = "alice@example.com" SELECT * FROM users WHERE email = 'alice@example.com' // A normal, valid comparison — one email, one match // Malicious input: email = "' OR '1'='1" SELECT * FROM users WHERE email = '' OR '1'='1' // The attacker's own quote closed the string early — // everything after it is no longer "data inside quotes," // it's now real SQL the database will execute
Same template, same code — only the input changed

The quote character in the attacker's input isn't just an unusual value — it's a boundary marker. The template's own opening ' plus the attacker's leading ' together close the string almost immediately, so OR '1'='1' stops being text stuck inside quotes and becomes a literal, working piece of SQL. And '1'='1' is always true — comparing the string 1 to itself. An OR with something always-true makes the entire WHERE clause always true, so the query returns every row in the table instead of the one it was supposed to filter for. That's the classic version of this bug bypassing a login check: no valid password required, because the query was never really asking "does this password match" anymore.

Why the parameterized version is actually safe

String concatenation is like handing someone a blank contract and letting them write directly in the blank space — if their handwriting runs past the line, they've added real new clauses to the document, and the notary reads all of it as part of the contract. A parameterized query is like a sealed, pre-printed form with a slot for a labeled index card. No matter what's written on that card — even if it's the word "clause" or contains punctuation — it goes into the slot as a single answer. It can never be mistaken for new wording in the contract, because the contract's structure was already locked in and parsed before the card ever arrived. That's the real mechanism behind $1: the database commits to "compare email to exactly one value" first, and only afterward drops in whatever the value happens to be, with no opportunity for it to reshape the query around itself.

ORMs like Prisma parameterize queries by default, which is a real, practical reason they reduce this entire class of bug — but it's worth knowing why it's safe, not just that it is.

CSRF — cross-site request forgery

CSRF tricks a logged-in user's browser into sending a request they didn't intend — e.g. a malicious page auto-submits a form to your bank's "transfer money" endpoint while you're still logged in elsewhere, and your browser happily attaches your real session cookie. It's different from XSS: CSRF doesn't need to read anything, it just needs your browser to send a request with credentials already attached.

The main defense

SameSite cookies. Setting sameSite: 'strict' or 'lax' on your auth cookie tells the browser not to send it along with requests originating from other sites — closing off most CSRF attacks without any extra token infrastructure.

Rate limiting & security headers
Rate limiting

Caps how many requests a client can make in a window of time — protects against brute-force login attempts and abusive traffic. Same underlying idea as rate limiting on a proxy, applied to your whole app.

Security headers

helmet.js sets a batch of sensible HTTP security headers automatically — things like disabling content sniffing and controlling what content sources a page can load from — for effectively one line of setup.

Quick reference — what each attack targets
SQL injection

Malicious input changes the structure of a database query. Fixed by parameterized queries / ORMs.

XSS

Malicious JavaScript gets injected into a page and runs in other users' browsers. Fixed by escaping output and HttpOnly cookies.

CSRF

A user's browser is tricked into sending an authenticated request they didn't intend. Fixed by SameSite cookies.

Brute force / abuse

Attacker hammers an endpoint with requests (login guesses, scraping). Fixed by rate limiting.

Interview-ready reasoning
What to say when this comes up

"What security measures would you add to this API?"

  • Validate every input at the boundary with a schema library — never trust the shape or content of a request.
  • Use parameterized queries or an ORM — never string-concatenate user input into SQL.
  • Set SameSite on auth cookies to cut off most CSRF attacks for free.
  • Rate limit sensitive endpoints — especially login and anything that touches money or sends messages.
  • Add helmet.js for a solid baseline of security headers with almost no effort.
