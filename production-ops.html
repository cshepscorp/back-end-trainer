Production & operations basics

What changes once real users depend on your app staying up — logging, error handling, graceful shutdown, and environment configs.

Structured logging

console.log is fine locally, but in production you need logs that are searchable and machine-parseable — structured as JSON with consistent fields, not free-form text. A request ID (or correlation ID) attached to every log line for a given request lets you trace one user's journey through your system, even across multiple services.

// Unstructured — hard to search or aggregate console.log('user 42 failed to login'); // Structured — queryable, consistent shape logger.error({ event: 'login_failed', userId: 42, requestId: req.id, reason: 'invalid_password' });
"Show me every failed login for user 42 last week" — trivial with structured logs, painful with plain strings
Error handling patterns
Operational errors

Expected failures that happen in normal operation — invalid input, a failed DB connection, a 404. Handle these gracefully and return a proper response.

Programmer errors

Actual bugs — calling a function with the wrong type, a typo. These usually mean something is broken and should be logged loudly, not quietly swallowed.

A centralized Express error-handling middleware (the one with 4 arguments — err, req, res, next) is where you catch both kinds, log appropriately, and send a consistent error response shape to the client instead of scattering try/catch blocks with inconsistent responses across every route.

Graceful shutdown
The problem

Killing a process instantly mid-request cuts users off in the middle of something — a half-finished database write, a dropped response the client never receives. When your process gets a SIGTERM (the signal sent before a deploy, restart, or scale-down), the right move is to stop accepting new requests, finish the ones already in flight, close database connections cleanly, and only then exit.

// Listen for the shutdown signal and drain in-flight work first process.on('SIGTERM', async () => { server.close(async () => { await db.$disconnect(); process.exit(0); }); });
server.close() stops new connections but lets existing ones finish
Environment configs & health checks
Environment separation

Dev, staging, and production typically need different database URLs, API keys, and log verbosity. Keeping these in environment variables (not hardcoded, not in one shared file) is what makes the same codebase safely deployable to all three.

Health checks

A simple /health endpoint that returns 200 if the app (and its DB connection) is actually working. Load balancers and orchestration tools poll this to decide whether to route traffic to an instance — or restart it.

CI/CD & containers, at a glance

Docker packages your app with everything it needs to run — same environment on your laptop, in staging, and in production, eliminating "it works on my machine." CI/CD automates running tests and deploying on every push, so shipping isn't a manual, error-prone ritual. You don't need deep expertise here for most interviews — being able to explain what problem each one solves is usually enough at the fundamentals level.

Interview-ready reasoning
What to say when this comes up

"What would you add before this goes to production?"

  • Structured logging with request IDs — so a failure can actually be traced, not just noticed.
  • A centralized error handler — consistent responses, proper logging, no scattered try/catch inconsistency.
  • Graceful shutdown handling — so deploys and restarts don't cut users off mid-request.
  • Environment-specific config via env vars — never hardcoded secrets or URLs.
  • A health check endpoint — so infrastructure can tell if the app is actually healthy, not just running.
